# Maintenance: development, release and signing

Notes for the author. Nothing here is needed to use the script.

## 1. Initial publication (done in 1.0.3, kept for reference)

1. The user name `jps-34` is already in place everywhere (READMEs, repository page, script
   headers), and the update repository is already built in `docs/`. To rebuild it after changing
   the scripts:

   ```bash
   python3 tools/build_repo.py --user jps-34
   ```

2. Create the `Badassium238` repository on GitHub (public), then:

   ```bash
   git init && git add . && git commit -m "Badassium238 1.0.3"
   git branch -M main
   git remote add origin git@github.com:jps-34/Badassium238.git
   git push -u origin main
   ```

3. On GitHub: *Settings > Pages > Build and deployment > Deploy from a branch*, branch `main`,
   folder `/docs`. The PixInsight repository is then served at
   `https://jps-34.github.io/Badassium238/`.

4. Test: in PixInsight, *Resources > Updates > Manage Repositories*, add this URL, then
   *Check for Updates*. Until it is signed, the *Allow unsigned update repositories* security
   option is required.

## 2. Signing (once and for all)

References: [Script code signing](https://pixinsight.com/doc/docs/ScriptCodeSigning/ScriptCodeSigning.html)
and [Update repositories](https://pixinsight.com/doc/docs/PIRepositoryReference/PIRepositoryReference.html).

1. **Keys**: **SigningKeys** script (shipped with PixInsight). It creates a key pair in a
   password-protected `.xssk` file. Use a very strong password, keep the file backed up offline,
   **never in Git** (the `.gitignore` excludes it).
2. **Certified developer status (CPD)**: **SubmitCPD** script, with a developer identifier, the
   public key and an e-mail address. The PixInsight team reviews the request and gets back in touch
   if needed. It is an identity check, not a code review. Without this status, the signature is
   only recognised on your own machines.

## 3. dev branch, then production

`main` = production: GitHub Pages serves `docs/` from `main`, so everything that lands on `main`
reaches PixInsight users. A new version goes to `dev` first.

**Only source to edit: `scripts/Badassium238.js`** (V8, PixInsight 1.9.4 and later).
`scripts/legacy/Badassium238_PI193.js` is version 1.1.1, frozen for PixInsight 1.8.9-3 to 1.9.3
(1.1.1 = 1.1.0 with the GPL licence header only): it is no longer touched, PixInsight is retiring that engine. `docs/` (archives, digests,
`updates.xri`) is generated by `python3 tools/build_repo.py --user jps-34`; it automatically keeps
the 1.1.1 package for the 1.8.9-3 to 1.9.3 range and the current package for 1.9.4 and later.

Putting a new version on dev (example with the 1.2.3 archive):

```bash
cd <local repository folder>/Badassium238
git switch dev
git rm -rq .
unzip -o <download folder>/Badassium238-v1.2.3.zip -d /tmp/b238
cp -a /tmp/b238/Badassium238/. .
git add -A
git status                     # check the list before committing
git commit -m "Badassium238 1.2.3"
git push
```

Test in PixInsight: *Script > Execute Script File*, pick `scripts/Badassium238.js` in the local
repository. The script runs without being installed; the production version stays in place.

Releasing once validated:

```bash
git switch main
git merge dev
git tag -a v1.2.3 -m "Badassium238 1.2.3"
git push origin main --tags
git switch dev
```

Then, in PixInsight, *Resources > Updates > Check for Updates*.

With signing (later), order matters: sign `scripts/Badassium238.js` with **CodeSign**, run
`python3 tools/build_repo.py --user jps-34`, sign `docs/updates.xri` last, then commit.

## 4. Versions and history

* Numbering `MAJOR.MINOR.PATCH`: patch = bug fixed with no intended change in results, minor = new
  feature, major = incompatible settings or results.
* Each published version has its `vX.Y.Z` tag. The PixInsight repository (`docs/`) only serves
  the latest one; older versions stay available through git.
* Full history: `git log --oneline --decorate`.
* Getting a file from an older version:
  `git show v1.0.3:scripts/Badassium238.js > Badassium238-1.0.3.js`

## 5. Fallback: editing through the GitHub website (without git)

Keep this for small text fixes (README, CHANGELOG). Note: a change made on the website in the
`main` branch is published immediately. For a script, go through dev.

1. On the repository page, open the relevant folder, then *Add file > Upload files* and drop the
   modified files: a file with the same name replaces the old one.
2. *Commit changes*. Then run `git pull` on `main` and `git merge main` on dev.
